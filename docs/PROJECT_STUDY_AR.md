## 1. هوية المشروع

المشروع مستودع لأتمتة تجهيز خوادم Ubuntu وإدارة خدماتها باستخدام Ansible. لا يحتوي تطبيق أعمال Django أو شيفرة Odoo نفسها؛ يحتوي إجراءات لجلب التطبيقات وتثبيتها وإعدادها. يجمع بين مرحلة تثبيت Ansible، وأمثلة تكامل، وتنفيذ أولي أوسع للبنية التحتية، وإعداد لوحة Semaphore.

القرار المعلن في README هو تثبيت Ansible مباشرة على Ubuntu باستخدام pipx أو apt. وجود Docker هنا له غرضان منفصلان: إدارة حاويات التطبيقات، وتشغيل Semaphore. لا يثبت ملف Compose وحده كيف أُعدّت مهام Semaphore أو أين ينفذ كل مشروع Ansible.

## 2. خريطة المكونات الفعلية

- `01-Installation/scripts/`: فحص البيئة، تثبيت Ansible، التحقق، ونسخ الحزمة إلى `/opt` مع رفض الكتابة فوق هدف موجود.
- `VERIFY_INSTALLATION.sh`: واجهة تستدعي سكربت التحقق. يتحقق من أوامر Ansible وPython وlocalhost ping ثم يجمع بعض facts.
- `02-Integration/`: هيكل توثيقي وأمثلة `.yml.example`. مثال نشر Odoo ينفذ رسالة تذكيرية فقط، وليس نشرًا.
- `InfrastructureAutomation/`: المشروع التنفيذي الأوسع؛ 8 أدوار و12 Playbook، مع inventories للتطوير والتجربة والإنتاج وقوالب ومتغيرات.
- `ansible.cfg` و`inventories/dev/hosts.yml` و`playbooks/system/health_check.yml`: مسار مستقل ومحدود لفحص localhost وعرض النظام والذاكرة والحمل.
- `automation/ansible-project/`: مشروع صغير يعرض معلومات الخادم. محتواه مطابق بايتًا للنسخة داخل `02-Integration/ansible-project/` وقت الفحص. ملف التشغيل اسمه `server_info.ymly`؛ امتداد غير معتاد قد يفوّت عمليات الاكتشاف المعتمدة على `.yml`، وليس دليلًا وحده على بطلان محتواه.
- `control-plane/semaphore/compose.yaml`: حاوية Semaphore بالإصدار المثبت في الملف `v2.19.12`، منفذ 3000، قاعدة SQLite، وvolume دائم. كلمات المرور ومفتاح التشفير مأخوذة من متغيرات البيئة.
- `docs/` وتقارير الجذر: وصف الخطط والحالة؛ توجد اختلافات بينها تستدعي تسوية الأدلة.

## 3. كيف ينتقل التنفيذ

المسار المفاهيمي:

```text
المشغل / مهمة معدّة في Semaphore مستقبلًا
  -> ansible-playbook + اختيار inventory وإعدادات المشروع
  -> تحديد مجموعة الخوادم والمتغيرات والصلاحيات
  -> gather_facts على الهدف عبر local أو SSH
  -> roles/tasks
  -> إنشاء إعدادات من templates وتثبيت حزم وإدارة خدمات
  -> notify للـhandlers عند حدوث تغييرات
  -> فحوص الخدمة وتقارير التنفيذ
```

اختيار المجلد وإعداد Ansible مهم لأن المستودع يحتوي عدة `ansible.cfg` مختلفة. إعداد الجذر يستهدف localhost، بينما إعداد `InfrastructureAutomation` يحدد roles وinventory آخر وتصعيدًا إلى root. يجب تثبيت طريقة تحميل الإعداد والمتغيرات قبل اعتماد أوامر التشغيل؛ وجود `group_vars/all.yml` في مجلد أعلى لا يغني عن التحقق من تحميله مع مواضع inventory/playbook الحالية.

الـPlaybooks مستقلة، ولا يوجد ملف جامع يضمن ترتيب جميع الاعتماديات. العلاقة المنطقية المقصودة هي تجهيز النظام ثم قواعد البيانات والخدمات ثم التطبيقات والتوجيه والفحوص والنسخ الاحتياطي. يجب تحويل هذه العلاقة إلى ترتيب متحقق منه قبل التنفيذ.

## 4. مسؤولية كل دور

- `common`: الحزم الأساسية وNTP وSSH وUFW والمراقبة والتحديثات التلقائية.
- `system`: يستدعي `common`، ثم ترقيات النظام وإعادة التشغيل المشروطة والمستخدمين وsudo وSSH keys وfail2ban. يستدعي `system_preparation.yml` دور `common` أيضًا، لذلك يوجد تداخل في مسار التجهيز.
- `docker`: مستودع حزم Docker وتثبيت Engine/Compose/Buildx، إعداد daemon، الشبكات والحاويات. بيانات الحاويات والشبكات قوائم متغيرات وليست تعريفات جاهزة لنشر Odoo.
- `postgresql`: حزم قاعدة البيانات، المستخدمون والقواعد، ملفات الإعداد، وجدولة النسخ والفحص. المتغير `postgresql_version` يستخدم في المسار، بينما الحزم غير مثبتة على ذلك الإصدار في المهمة.
- `odoo`: إنشاء المستخدم والمجلدات، إعداد الخدمة، استنساخ فرع Odoo، تثبيت متطلبات Python، جلب الإضافات والنسخ والفحص. التنفيذ Native من المصدر وsystemd، وليس Docker Compose.
- `traefik`: ملفات إعداد ثابتة وديناميكية، تنزيل executable وتشغيل systemd، وتوجيه إلى عناوين backend من المتغيرات.
- `django`: جلب مستودع خارجي، بيئة Python، إعدادات وملف بيئة، migrations وcollectstatic وخدمة Gunicorn. يكتب `settings.py` عامًا فوق إعداد المشروع المستهدف، مما قد يزيل تعريفات تطبيقاته الخاصة.
- `backup`: سكربتا backup/restore وcron وmanifest. الـPlaybook المسمى `backup.yml` ينفذ مهام مباشرة ولا يستدعي هذا الدور؛ بالتالي هناك مساران مختلفان للنسخ.

مسار الطلب المقصود بعد اكتمال النشر: العميل → Traefik على 80/443 → Odoo أو Gunicorn → PostgreSQL. هذا وصف للإعدادات والقوالب، وليس شبكة تشغيل تم التحقق منها.

## 5. حالة الاكتمال والأدلة

`INSTALLATION_REPORT.md` بتاريخ 2026-11-07 يقول إن التثبيت والتحقق لم ينفذا من تلك البيئة، ولم يعتمد الانتقال للمرحلة الثانية. `docs/REPOSITORY_AUDIT.md` يذكر نجاح localhost وخدمات فعلية، لكن لا يرفق مخرجات تشغيل تثبتها في الملفات المفحوصة. `InfrastructureAutomation/docs/IMPLEMENTATION_REPORT.md` بتاريخ 2026-11-17 يضع علامات اكتمال على مكونات كثيرة، مع وصف التنفيذ بأنه Scaffold.

لذلك التصنيف الأنسب: حزمة تثبيت موجودة، وهيكل أتمتة موسع منفذ جزئيًا، وجاهزية التشغيل المتكامل غير مثبتة. لم أتحقق من خادم بعيد أو حالة حاوية أو إصدار مثبت فعليًا. Jenkins مذكور في الخطة والمتغيرات دون Jenkinsfile أو تنفيذ تكامل ظاهر في جرد الملفات.

## 6. نتائج مهمة قبل التشغيل

### موانع ونواقص مباشرة

1. تسعة قوالب مستدعاة غير موجودة في أدوارها: `backup-manifest.j2`؛ `20auto-upgrades.j2`؛ `logrotate.j2`؛ `monitor.sh.j2`؛ `odoo-backup.sh.j2`؛ `pg-backup.sh.j2`؛ `logrotate-system.j2`؛ `jail.local.j2`؛ `traefik.service.j2`.
2. `InfrastructureAutomation/handlers/main.yml` موجود دون استيراد ظاهر في الـPlaybooks. مجلد handlers العام لا يصبح handlers للأدوار تلقائيًا. الموجود محليًا في دور common يعالج خدمات محدودة فقط؛ إشعارات مثل restart docker وreload systemd تحتاج ربطًا فعليًا. توجد أيضًا إشعارات بلا تعريف مطابق، مثل reload postgresql وupdate motd.
3. في `roles/django/tasks/main.yml` كلمة `becomes: false`، كما تُنشأ المجلدات بملكية django قبل إنشاء المستخدم، مما يعرقل المضيف الجديد.
4. مهام UFW تستخدم `state: allowed` بدل إعداد قاعدة `rule: allow`. كما تفعل سياسة المنع قبل إضافة السماح لـSSH.
5. Playbooks Docker تستهدف `docker_servers`، بينما inventories المرفقة لا تعرف هذه المجموعة. مجموعات الخدمات في inventory التطوير خالية؛ التشغيل دون تطابق قد يتجاوز العمل بدل إثبات نجاحه.
6. إعداد Traefik الافتراضي `v3.x` ليس رقم إصدار تنزيل محددًا، وبناء الرابط يضيف `v` أخرى.

### عزل Odoo غير مكتمل

Playbook الإصدار 17 وPlaybook الإصدار 19 يستهدفان مجموعة `odoo_servers` نفسها، بما فيها مضيفا الإصدارين في inventory الإنتاج. يتغير فرع المصدر واسم الخدمة، لكن الإعداد والبيانات والمنفذ وقاعدة البيانات مشتركة افتراضيًا. الخدمتان تقرآن `/etc/odoo/odoo.conf` وتستخدمان افتراضيًا 8069 و`/var/lib/odoo`. تشغيل الملفين على المضيف نفسه قد يكتب إعدادًا فوق الآخر ويتسبب في تعارض المنافذ.

كما أن مهمة نشر config تستخدم `odoo_config_dir` دون default رغم استعمال default في إنشاء المجلد، وملف الخدمة لا يستخدم Python الموجود داخل venv الذي أنشأته مهام التثبيت. ملف config مملوك root:root بصلاحية 0640 بينما الخدمة تعمل بمستخدم odoo، مما يستدعي معالجة صلاحية القراءة.

### النسخ والاستعادة

`playbooks/backup.yml` ودور backup يستخدمان عمرًا سالبًا في `find` مع وسيط `age_suffix` غير موثق للوحدة. العمر السالب يحدد الملفات الأحدث من الحد، لا النسخ الأقدم؛ لذلك إصلاح الوسيط وحده لا يصلح سياسة الاحتفاظ. راجع [توثيق find الرسمي](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/find_module.html).

النسخ العام يستثني بيانات PostgreSQL وDocker، فلا يثبت حماية قواعد البيانات. قالب نسخ PostgreSQL نفسه غير موجود. سكربت النسخ ينتهي بـexit 0 ولا يوقف التنفيذ عند فشل tar، والاستعادة تخفي أخطاء النسخ باستخدام `|| true`. Playbook الاستعادة يفك الأرشيف في مجلد مؤقت دون مهمة تسبقه بإنشائه. لا توجد تجربة استعادة مثبتة.

### إعدادات وحماية الوصول

- inventories تستخدم `StrictHostKeyChecking=no` رغم تفعيل host_key_checking في ansible.cfg.
- الملف `control-plane/semaphore/key-acess.txt` (الآن تحت `legacy/`) كان متتبعًا ويتضمن تعيينات بأسماء كلمة مرور المدير ومفتاح تشفير Semaphore. لم أنقل قيمه إلى التقرير. أُزيل من تتبّع Git وبقي محليًا ومتجاهلًا؛ يجب اعتبار أي قيمة نُشرت سابقًا مخترقة وتدويرها.
- قوالب SSH تستبدل إعداد الخادم وتحدد AllowUsers دون فحص `sshd -t` ظاهر قبل التطبيق.
- مفاتيح SSH داخل `group_vars/all.yml` تحتوي مسافات مثل `ssh PasswordAuthentication`، بينما القالب يستعمل قيمًا ثابتة لهذه الخيارات.

توثيق داعم: [تحميل roles وhandlers](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_reuse_roles.html)، [خيارات UFW](https://docs.ansible.com/projects/ansible/latest/collections/community/general/ufw_module.html).

## 7. ما تم التحقق منه محليًا

- جرد 106 ملفات خارج `.git` قبل إضافة هذا التقرير؛ منها 8 أدوار و12 Playbook في المشروع الموسع.
- قراءة المهام والقوالب والإعدادات الأساسية ومقارنة النسختين الصغيرتين من ansible-project.
- تحليل 40 ملف YAML/أمثلة YAML بنجاح باستخدام PyYAML. تعذر قراءة `02-Integration/collections/requirements.yml.example` بترميز UTF-8؛ هذا فشل ترميز وليس تشخيصًا لبنية YAML.
- مطابقة مراجع قوالب الأدوار مع الملفات وكشف القوالب التسعة الناقصة.
- لا يتوفر ansible أو ansible-playbook على PATH في جلسة PowerShell الحالية؛ لم أنفذ Ansible syntax-check أو اختبارات idempotency أو نشرًا. نجاح YAML parser لا يثبت صحة وحدات Ansible أو القوالب أو الاتصال.

## 8. ترتيب التطوير المقترح

1. تحديد مشروع Ansible المرجعي وطريقة تحميل config وinventory والمتغيرات، وتسوية تقارير الحالة دون حذف الأدلة القديمة.
2. إكمال القوالب والـhandlers، وإصلاح المهام غير الصالحة، وتعريف متطلبات collections بطريقة قابلة للتثبيت.
3. فصل Odoo 17 و19 بالمجموعات والمنافذ والمستخدمين والبيانات والإعدادات وقواعد البيانات.
4. إصلاح النسخ والاستعادة وإثبات استعادة قاعدة وfilestore في بيئة معزولة.
5. تشغيل syntax-check ثم تجارب تطوير واختبار إعادة التنفيذ لكل Playbook، مع التحقق من بقاء الوصول عبر SSH.
6. ربط Semaphore بمهام ومستودع وinventory واعتمادات محددة بعد ثبوت نجاح التنفيذ المباشر، ثم تنفيذ CI/CD المخطط له.

لم تتغير ملفات التشغيل خلال هذه الدراسة؛ الإضافة الوحيدة هي هذا التقرير.
