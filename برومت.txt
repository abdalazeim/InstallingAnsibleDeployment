# المشروع: InstallingAnsibleDeployment
## منصة احترافية لأتمتة البنية التحتية وإدارة خوادم Ubuntu باستخدام Ansible وSemaphore

# 1. الدور والهدف الرئيسي

تصرّف بصفتك مهندس DevOps خبيراً، ومهندس بنية تحتية، ومهندس Ansible Automation، ومسؤول أنظمة Linux، ومطور حلول أتمتة باستخدام Python.

مهمتك هي دراسة وتطوير المستودع الحالي:

https://github.com/abdalazeim/InstallingAnsibleDeployment

وتحويله إلى منصة احترافية متكاملة لإدارة البنية التحتية وخوادم Ubuntu باستخدام Ansible، مع جعل **Ansible Semaphore UI واجهة الإدارة والتنفيذ الرئيسية لجميع العمليات**.

الهدف هو بناء منتج قابل للتثبيت والتشغيل على أي خادم Ubuntu Server متوافق، دون الاعتماد على جهاز التطوير الحالي أو إعداداته الخاصة.

يجب أن يتمكن مسؤول النظام من الدخول إلى واجهة Semaphore، واختيار المشروع والبيئة والخادم والعملية المطلوبة، ثم تنفيذها ومتابعة نتائجها دون الحاجة إلى تشغيل الأوامر يدوياً في Terminal لكل عملية.

## الهدف النهائي

عند فتح Semaphore UI يجب أن يجد المسؤول مشروعاً باسم:

Infrastructure Automation

ويحتوي المشروع على:

- Repositories.
- Inventories.
- Environment.
- Key Store.
- Templates.
- Task History.
- Schedules.

ويجب أن تحتوي Templates على عمليات الإدارة الفعلية، مقسمة إلى مجموعات واضحة:

1. Ubuntu Server Management.
2. Docker Infrastructure.
3. Odoo Management.
4. PostgreSQL Administration.
5. Traefik & Networking.
6. Django Applications.
7. Jenkins Integration.
8. Backup & Recovery.
9. Monitoring & Health Checks.

**مهم جداً:** لا يكفي إنشاء ملفات Playbooks داخل المستودع. يجب تجهيزها وربطها فعلياً بقوالب Templates قابلة للتنفيذ من Semaphore UI.

لا تنشئ مشروعاً منفصلاً عن المستودع الحالي، ولا تحذف أي تنفيذ موجود قبل دراسته وفهم علاقاته.

## الوحدة الأولى: Ubuntu Server Management

الأولوية: حرجة.

تطوير وحدة متكاملة لإدارة خادم Ubuntu.

### A. معلومات النظام

اجمع المعلومات التالية:

- إصدار Ubuntu.
- إصدار Kernel.
- معلومات CPU.
- معلومات RAM.
- معلومات Swap.
- مساحة الأقراص.
- أنظمة الملفات.
- وحدات التخزين المركبة.
- واجهات الشبكة.
- عناوين IP.
- Hostname.
- مدة تشغيل النظام.
- الخدمات العاملة.
- استهلاك موارد النظام.

يجب توفير Playbook يعرض المعلومات بصيغة مفهومة، مع إمكانية إخراج JSON.

### B. إدارة تحديثات النظام

نفّذ:

- تحديث APT.
- تحديث الحزم.
- تحديثات الأمان.
- تثبيت الحزم.
- حذف الحزم.
- التحقق من الحزم.
- تنظيف الحزم غير المستخدمة.
- اكتشاف الحاجة إلى إعادة التشغيل.
- إعادة تشغيل النظام عند الموافقة.

الشروط:

- دعم Check Mode.
- دعم Dry Run.
- عدم إعادة تشغيل الخادم تلقائياً دون موافقة صريحة.
- إصدار تقرير بعد التنفيذ.

### C. إدارة المستخدمين والصلاحيات

نفّذ:

- إنشاء المستخدمين.
- تعديل المستخدمين.
- حذف المستخدمين.
- إدارة المجموعات.
- إضافة المستخدمين إلى المجموعات.
- إعداد صلاحيات sudo.
- إدارة SSH Authorized Keys.
- قفل الحسابات وفتحها.
- التحقق من الصلاحيات.

لا تعدّل حساب المسؤول الحالي بطريقة قد تؤدي إلى فقدان الوصول.

لا تعرض كلمات المرور في السجلات.

### D. إدارة SSH

نفّذ:

- تثبيت OpenSSH Server.
- إدارة إعدادات SSH.
- تغيير المنفذ.
- تقييد دخول root.
- إعداد Password Authentication.
- إعداد Public Key Authentication.
- فحص خدمة SSH.
- إنشاء نسخة احتياطية من الإعدادات.

تحقق من صحة الإعدادات قبل إعادة تشغيل SSH.

لا تطبق تغييرات قد تؤدي إلى منع المسؤول من الدخول إلى الخادم.

### E. إدارة Firewall

استخدم UFW.

نفّذ:

- تثبيت UFW.
- تفعيل وتعطيل Firewall بموافقة.
- إضافة قواعد Allow وDeny.
- حماية SSH.
- فتح منافذ التطبيقات.
- التحقق من القواعد.
- عرض حالة Firewall.

لا تفعّل UFW قبل التأكد من السماح باتصال SSH.

### F. مراقبة موارد الخادم

اجمع:

- CPU Usage.
- RAM Usage.
- Swap Usage.
- Disk Usage.
- Inode Usage.
- Load Average.
- Network Information.
- System Uptime.

أنشئ تقارير JSON قابلة للاستخدام لاحقاً في Django.

### B. عمليات Odoo

وفّر:

- تشغيل Odoo.

### C. النسخ الاحتياطي لقاعدة البيانات

دعم:

- PostgreSQL Custom Format.
- SQL Backup.
- Compression.
- Timestamped Backups.
- Retention Policies.
- Backup Metadata.
- Integrity Verification.

### D. النسخ الاحتياطي لـ Filestore

نفّذ:

- اكتشاف Filestore الصحيح.

- ضغط النسخ.

- ربط نسخة قاعدة البيانات بنسخة Filestore الخاصة بها.

يجب أن تتضمن النسخة الاحتياطية الكاملة لـ Odoo قاعدة البيانات وFilestore معاً.

### E. استعادة النسخ الاحتياطية

اعتمد الخطوات التالية:

1. فحص ملفات النسخة.
2. التحقق من Checksums.
3. التحقق من توافق قاعدة البيانات.
4. إنشاء وجهة الاستعادة.
5. استعادة قاعدة البيانات.
6. استعادة Filestore المرتبط بها.
7. ضبط الصلاحيات.
8. التحقق من تشغيل Odoo.
9. تنفيذ Health Checks.

لا تستبدل قاعدة إنتاج موجودة دون موافقة صريحة.

### F. إدارة Custom Addons

وفّر:

- اكتشاف مجلدات Addons.
- فحص بنية Addons.
- نشر Addons.
- تحديث Addons من Git.

# 5. التكامل الرئيسي مع Semaphore UI

## هذا القسم من أهم متطلبات المشروع

يجب أن يكون Semaphore هو واجهة إدارة وتنفيذ عمليات Ansible.

لا يكفي إعداد Playbooks أو إنشاء مجلد باسم semaphore داخل المستودع.

المطلوب هو إعداد المستودع بطريقة تسمح بربطه بمشروع Semaphore، وإنشاء Templates منظمة وقابلة للتشغيل من الواجهة.

## A. إنشاء مشروع Semaphore

يجب تجهيز مشروع باسم:

Infrastructure Automation

ويجب توثيق طريقة إنشائه وربط إعداداته.

يجب أن يحتوي المشروع على العناصر التالية:

| القسم | المحتوى |
|---|---|
| Projects | Infrastructure Automation |
| Repositories | مستودع GitHub الخاص بالمشروع |
| Inventory | Build / Dev / Staging / Prod |
| Environment | متغيرات التشغيل والبيئة |
| Key Store | مفاتيح SSH وAnsible Vault |
| Templates | قوالب تنفيذ Playbooks |
| Task History | سجل عمليات التنفيذ |
| Schedules | المهام المجدولة |

استخدم أسماء الأقسام والإمكانات التي يدعمها إصدار Semaphore المثبت فعلياً، ولا تفترض وجود ميزة غير مدعومة.

## B. ربط GitHub Repository

اربط مستودع:

InstallingAnsibleDeployment

بمشروع Infrastructure Automation داخل Semaphore.

المتطلبات:

- استخدام Repository URL.
- دعم Git Authentication عند الحاجة.
- تحديد Branch.
- تحديد مسار Playbooks.
- تحديث المستودع عند تنفيذ المهام وفق إعدادات Semaphore.
- التحقق من إمكانية الوصول إلى ملفات Playbooks.
- توثيق طريقة تحديث المستودع.

لا تضع GitHub Tokens أو كلمات المرور داخل ملفات المستودع.

## C. إعداد Inventories

أنشئ Inventories للبيئات:

1. Build.
2. Dev.
3. Staging.
4. Prod.

# 9. واجهة CLI

أنشئ CLI احترافياً باسم:

`infrastructure-manager`

يكون CLI واجهة خفيفة لتشغيل Playbooks المعتمدة، ولا يستبدل Semaphore UI.

أمثلة:

```bash
infrastructure-manager system info
infrastructure-manager system update
infrastructure-manager system users list
infrastructure-manager system firewall status

infrastructure-manager docker list
infrastructure-manager docker start <container>
infrastructure-manager docker stop <container>
infrastructure-manager docker restart <container>

infrastructure-manager odoo list
infrastructure-manager odoo status 19
infrastructure-manager odoo backup 19

infrastructure-manager postgres databases list
infrastructure-manager postgres backup <database>

infrastructure-manager traefik status
infrastructure-manager django deploy <application>

infrastructure-manager backup list
infrastructure-manager monitoring health
```

دعم الخيارات:

- `--inventory`
- `--limit`
- `--check`
- `--diff`
- `--verbose`
- `--timeout`
- `--json`

لا تسمح بتنفيذ أوامر Shell عشوائية من المستخدم.

# 10. معالجة الأخطاء وسلامة التنفيذ

يجب أن تطبق جميع Playbooks:

- التحقق من المدخلات.
- التحقق من المتطلبات.
- فحص الإعدادات قبل التغيير.
- استخدام Handlers.
- اكتشاف فشل العمليات.
- حفظ السجلات.
- عرض رسائل خطأ مفهومة.
- منع العمليات التدميرية افتراضياً.
- دعم Check Mode عند الإمكان.
- دعم Rollback عند الإمكان.

تتطلب العمليات التالية موافقة صريحة:

- حذف قاعدة بيانات.
- استعادة قاعدة بيانات.
- حذف مستخدم.
- حذف Container.
- حذف Docker Volume.
- تغيير Firewall.
- نشر تطبيق في Production.
- إعادة تشغيل النظام.

استخدم متغيراً مثل:

```yaml
confirm_destructive_operation: false
```

اجعل الوضع الافتراضي آمناً.

يجب أن تحتوي Templates الحساسة على متغيرات تأكيد واضحة، وألا تنفذ عمليات الحذف أو الاستعادة بمجرد الضغط على Run دون التحقق من الموافقة.

# التعليمات النهائية

طوّر منتجاً حقيقياً لإدارة البنية التحتية، وليس مجرد مجموعة Playbooks تجريبية.

يجب أن يكون المشروع:

- قابلاً للتثبيت على خوادم Ubuntu مختلفة.
- قابلاً للصيانة والتطوير.
- آمناً.
- معيارياً.
- قابلاً لإعادة الاستخدام.
- متكاملاً مع Semaphore UI.
- قابلاً للتوسع مستقبلاً مع Django Infrastructure Manager.

اجعل Semaphore UI واجهة التنفيذ والتحكم الرئيسية لعمليات Ansible.

عند الدخول إلى Semaphore يجب أن يتمكن المسؤول من اختيار مجموعة الإدارة، ثم اختيار العملية المطلوبة، وتحديد Inventory والخادم، وإدخال المتغيرات المطلوبة، وتشغيل المهمة ومتابعة نتيجتها.

لا تكتفِ بإنشاء ملفات Playbooks؛ أنشئ أيضاً الربط والتوثيق والإعدادات اللازمة حتى تظهر العمليات داخل Semaphore UI.

حافظ على الوظائف الحالية التي تعمل.

لا تختلق نتائج اختبارات ناجحة.

لا تستخدم إعدادات ثابتة خاصة بجهاز التطوير.

لا تنفّذ عمليات تدميرية على خادم التطوير.

ابدأ بمراجعة المستودع، ثم ضع خطة التنفيذ، وبعدها نفّذ التطوير على مراحل مع اختبار كل مرحلة.

**الأولوية القصوى: أن يكون Semaphore UI واجهة فعلية لإدارة وتشغيل ومتابعة جميع وحدات البنية التحتية، مع المحافظة على قابلية نقل المشروع إلى أي خادم Ubuntu آخر.**
